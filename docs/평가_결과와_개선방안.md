# 평가 결과와 개선 방안 · 프로젝트 의의 (4번, 2026-10-15)

> 실제 실행 기록(`eval/results/`)을 바탕으로 4번이 정리했습니다. 개선 방안의 담당 · 우선순위는 **4번 제안**이며, 팀 확인 후 확정합니다.
> 상세 보고서: `발표자료/평가_결과_보고서.pdf` · 숫자 원본: `eval/results/summary.json`, `eval/results/scorecard.md`

## 1. 한 줄 정리

**같은 모델(gpt-4o-mini)인데, 근거와 검사를 붙이자 공통 기준 통과가 0% → 57%가 됐습니다.**
틀린 답은 '검증 실패'로 알려 주고, 약점은 숫자로 찾아 고칠 곳과 순서를 정했습니다.

## 2. 무엇을 어떻게 평가했나

| | 비교 평가 | 자체 평가 |
|---|---|---|
| 묻는 것 | 일반 LLM보다 나은가? | 우리가 정한 규칙대로 동작하는가? |
| 대상 | 우리 챗봇 vs 일반 LLM | 우리 챗봇 |
| 기준 | 공통 채점 8항목 (두 답에 같은 잣대) | 팀 프롬프트 · 코드의 규칙 21항목, 100점 |
| 질문 | 1.x로 올리기 30 + 버전 오가기 6 | 위 36 + 분류 확인 14 (분류는 3회 반복) |

- 두 시스템 모두 **gpt-4o-mini, temperature 0**, 글자 하나 다르지 않은 같은 입력. 일반 LLM은 시스템 프롬프트 없이 (ChatGPT에 붙여 넣는 상황)
- 채점은 **LLM 없이 코드로**: 문법 · 옛 import · import 존재(2번 1.x 도구 목록) · 정의 안 된 이름 · 결과값 보존 · 남은 import · 정답 import · 실제로 바꿈

## 3. 강점 (숫자로 확인된 것)

| 강점 | 근거 |
|---|---|
| **같은 모델로 0% → 57%** | 공통 기준 8항목 모두 통과: 챗봇 57% · 일반 LLM 0% (1.x로 올리기 30개) |
| **실행되는 코드** | 정답 import를 빼고 '실행 기준'만 보면 87% vs 0% |
| **옛 import를 확실히 걷어냄** | 옛 import 없음 93% vs 3%, 새 import가 1.x에 실제로 있음 90% vs 3% |
| **환각을 '통과'로 내보내지 않음** | 일반 LLM은 30개 중 29개가 옛 코드 그대로인데 "1.x에 맞게 수정했다"고 답함. 챗봇은 실패한 답을 '검증 실패'와 이유로 표시 |
| **근거가 붙은 답** | 바뀐 줄 103개 중 96개(93%)에 근거 ID |
| **근거 검색 · 분석이 탄탄** | 대응표에 있는 옛 import 99%(80/81)를 근거로 가져옴, 목표 버전 읽기 100%, 코드 원문 추출 97% |
| **쉬운 · 경로형 문제는 완벽** | 쉬움 100%, import 경로 · 문서 로더 유형 100% (일반 LLM 0%) |
| **답변 규칙 · 안정성** | LangChain 질문 답에 '출처' 100%, 한국어 100%, 50개 모두 오류 없이 응답, 코드 변환 중앙값 11.6초 |
| **다시 고치는 루프** | 1회차 43% → 최종 53% (+10%p), 통과한 답은 평균 1.2회 |

## 4. 약점 → 강점으로 덮이는 것 · 고칠 것

| # | 약점 (근거) | 강점이 덮는 부분 | 개선 방안 | 담당 (제안) | 우선 |
|---|---|---|---|---|---|
| 1 | **질문 분류**: 고쳐 달라면서 에러 이유 · 설치 안내도 물으면 'LangChain 질문'으로 가서 코드를 안 고침. 30개 중 6개 (q06 · q07 · q09 · q20 · q26 · q28), 3회 반복해도 같음 | search 답에도 근거 문서와 코드가 있어 6개 중 3개는 공통 채점 통과 | 분류 규칙에 "코드가 있고 고치기 · 바꾸기 의도가 있으면 설명 요청이 섞여도 migration" 추가, classifier temperature 0.7 → 0 | 1번 | ① |
| 2 | **환각 (기록 없는 변경)**: 모든 시도의 오류 1위 33회, 최종 실패 11건 중 9건 | 검사기가 전부 잡아서 환각이 '통과'로 나간 적 없음 | rewriter 프롬프트에 "요청 코드에 없던 줄 · 문서 예시 코드를 넣지 말 것", 환각을 만든 근거를 다음 시도에서 제외(`EVIDENCE_FAULT_TYPES`에 `unrecorded_change` 추가) | 3번 · 1번 | ② |
| 3 | **근거 ID 누락**: missing_evidence 23회, 최종 실패 4건 | 근거 없는 변경은 검사기가 막음 | `evidence_ids` 빈 목록을 구조화 출력 단계에서 거절, 재시도 피드백에 붙일 근거 후보 제시 | 3번 | ② |
| 4 | **검사기 빈틈 ①**: `result = chain.invoke(...)` 뒤 `result["text"]` (q10, 실행하면 TypeError)를 통과시킴 | 공통 채점(`eval/score.py`의 `lcel_subscript`)이 잡아냄 | verifier 10번을 변수에 담아 꺼내는 경우 · 체인 끝이 `ChatOpenAI(...)` 직접 호출인 경우까지 확장 | 3번 | ③ |
| 5 | **검사기 빈틈 ②**: 0.x로 되돌리는데 1.x 전용 `create_agent`를 쓴 코드가 통과 (q32). 버전 오가기 6개 중 정답 import 0개 | 목표 버전 읽기는 100% 정확 | verifier가 `target_version`을 받아 2번 `version_resolve`(버전별 도구 목록, 이미 있음)로 import 존재 확인 | 3번 · 2번 | ③ |
| 6 | **옛 창고 우회**: 최신 방식 대신 `langchain_classic`으로 3개 (q15 · q21 · q22) | 실행은 됨 (실행 기준 통과) | retriever가 대안(alternative) 사용법 문서를 함께 검색, 우회하면 notes에 "최신 방식 아님 + 대안" 필수 | 2번 · 3번 | ④ |
| 7 | **재시도 회복률 31%** (1회차 실패 16개 중 5개만 회복) | 실패는 숨기지 않고 화면에 이유 표시, '같은 요청으로 다시 시도' 버튼 | 2 · 3번 개선 후 다시 측정 (목표 50%) | 1번 · 3번 | ② 이후 |

**우선순위 이유**: ①은 규칙 한 줄로 6개가 바로 변환 경로로 들어오고, ②는 실패 원인 1 · 2위라 통과율에 가장 크게 영향을 주며, ③은 '통과'의 신뢰도 문제, ④는 품질 개선입니다.

**기대 효과 (추정)**: ①만으로 6개가 변환 경로에 들어오고, 변환 경로의 현재 통과율(1.x 24개 중 16개 ≈ 67%)이면 최종 검증 통과가 53% → 약 67%(20/30)까지 오를 수 있습니다. 개선 후 같은 스크립트(`eval/run_eval.py` → `eval/score.py`)로 다시 재서 비교합니다.

## 6. 버전 오가기 (참고, 6개)

- 챗봇: 목표 버전은 6개 모두 정확히 읽음, 검사기 통과 50%, **정답 import 0%** (검사기가 1.x 기준이라 1.x 경로를 그대로 둠)
- 일반 LLM: 정답 import 33%
- → 약점 5번을 고치면 바로 개선되는 영역. 표본이 작아 질문을 늘려 다시 측정할 계획

## 7. 프로젝트 의의

1. **"모델을 바꾸지 않고 신뢰를 만든다"를 숫자로 보였습니다.** 같은 gpt-4o-mini가 혼자서는 0%, 근거(대응표 · 공식 문서) + 코드 검사(11가지) + 재시도를 붙이면 57%(실행 기준 87%).
2. **버전 지체 환각을 실제로 재현하고 막았습니다.** 일반 LLM은 옛 코드를 "수정했다"고 돌려줬고(29/30), 챗봇은 같은 상황을 검사로 걸러 '검증 실패'로 알렸습니다.
3. **틀릴 때 틀렸다고 말하는 AI.** 답마다 근거(93%)와 검사 결과를 보여 주므로 사용자가 직접 확인할 수 있습니다.
4. **스스로 점검하는 구조.** 팀 규칙 21가지를 실행 기록으로 채점하는 도구(`eval/score.py`)를 만들어, 고칠 곳과 순서를 데이터로 정했습니다. 개선 후 같은 도구로 다시 재면 효과가 숫자로 나옵니다.
5. **확장성.** 대응표 · 문서 · 검사 기준만 바꾸면 pydantic, OpenAI SDK처럼 빠르게 바뀌는 다른 라이브러리에도 같은 구조를 쓸 수 있습니다.

## 8. 한계

- 질문마다 1회 실행 (LLM 답은 매번 조금씩 달라 몇 %p는 오르내릴 수 있음, 분류만 3회 반복)
- 코드를 실제로 실행하지 않고 정적으로 확인 (실행 결과가 맞는지는 다음 단계: 가짜 LLM 실행 테스트)
- '정답 import'는 질문마다 한 가지 기준이라 다른 올바른 방법도 감점될 수 있음 → '실행 기준 통과'를 함께 표시
- 질문 30개는 팀이 직접 만든 것, 버전 오가기 6개는 표본이 작음
